# 设计决策：双模式架构（零部署信箱 + 直连会话）

日期：2026-08-18。状态：已采纳（v0.4.0）。

## 背景

v0.3.0 以自托管 TeamMCP 中转为唯一传输，要求团队先部署一台服务器。这与 DSH 插件
生态"装上即用"的分发预期冲突：陌生用户不会为了试一个插件先去架设后端。

同期评估过"纯 P2P + 公开 paste 网页信令"方案，未采纳为主架构，原因：

1. **离线送达是物理缺失**：P2P 管道要求双方同时在线；"发出去、对方明早收"是本
   项目的主场景，必须有常在线的存储点。
2. **频道广播缺失**：一发多收需要存储点或全员在线两两互联。
3. 公开 paste 服务在国内不可达；Node WebRTC 原生依赖安装失败率高，不能让核心
   功能依赖它。

## 决策

物理规律（异步+广播需要常在线存储点）不可回避，但"存储点"不必是用户部署的服务器
——**寄生在用户已有的基础设施上**：

- **信箱模式（默认）**：GitHub 私有仓库当信箱。频道=Issue、消息=评论。身份、ACL
  （协作者列表）、离线存储、审计历史、人类可用的网页界面全部白拿；配置缩到一个
  仓库名。代价：轮询延迟（秒级到半分钟），对异步协作场景可接受。
- **直连模式（并列一等公民）**：连接码（压缩 SDP）由人经任意聊天工具传递一次，
  之后 WebRTC DataChannel 机器直连，业务数据零第三方，会话即用即毁。人本来就有
  聊天渠道，这是唯一真正零第三方的信令路径。代价：双方须同时在线；对称 NAT 下
  可能失败——失败就明说，不引入 TURN 中转来"救"。
- **TeamMCP 中转降级为可选传输**：对延迟敏感且愿意自托管的团队保留。

两种模式对应人类通信的两个不可互替原语——邮件（异步存储转发）与电话（实时会话）。
所有入站消息不论来源，统一进入隔离收件箱、经人工放行才对模型可见。

## 后果

- 新用户上手成本：建一个私有仓库 + 互加协作者，无任何部署。
- 传输层接口化（`Transport`），未来可加飞书传输（国内非开发者团队）等实现。
- 远期优化已预留：信箱模式可充当直连会话的自动信令通道（免人工传码）；大文件
  经直连通道传输、信箱只传引用。
